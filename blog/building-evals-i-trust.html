Building evals I actually trust

A demo that works once is a magic trick. A system that works is a claim you can defend with a number. Most of my job lives in the gap between the two — and evaluation is the bridge.

Start with the question, not the metric

Before I reach for accuracy or F1, I ask what "good" even means for this feature. A retrieval answer can be fluent and confidently wrong. If the metric can't tell those apart, it's the wrong metric.

If you can't describe the failure you're afraid of, you can't measure whether you fixed it.

Build a tiny, honest dataset first

Twenty hand-labelled examples that cover the failure modes beat two thousand scraped ones that don't. I look for:

  • The easy cases (a sanity floor).
  • The adversarial cases (where it actually breaks).
  • The ambiguous cases (where even humans disagree).

Make it runnable in one command

An eval you have to babysit is an eval you'll skip under deadline. Mine run like tests: 

$ python eval.py --suite retrieval --n 200
faithfulness   0.91
answer_recall  0.84
latency_p95    810ms

Then I watch the number move as I change one thing at a time. That's the whole game: a baseline, a hypothesis, and a metric honest enough to tell me I was wrong.
